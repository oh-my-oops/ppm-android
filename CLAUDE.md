# android/ — native PPM client for Android (phone + tablet)

Plan: `plans/261019-2119-native-android-app/` (gitignored, in the main checkout). The port follows the Apple app (`~/Projects/ppm-apple/apple`, its `Packages/PPMKit` is the source of every rule here) and, behind both, the web (`src/web/`).

## Layout

- `core/protocol` — wire types. Frames are parsed into a kotlinx `JsonElement` first and read field by field (`Json.kt` extensions), so an unknown field or frame `type` never fails a decode.
- `core/client` — REST (`ApiClient` + `ApiClientSessions`/`ApiClientUploads` extensions), `SocketConnection` (OkHttp WebSocket as a channel of events, never reconnects by itself), `InflightGets` (identical GETs share one request, as `api-client.ts`), `ServerStore` (servers in a `KeyValueStore`, passwords in a `SecretStore`).
- `core/state` — `ChatTranscript` (pure reducer ported from `src/web/hooks/use-chat.ts`: frames in, `ChatEffect`s out), `ChatController` (history + socket + reconnect around it, publishes one `StateFlow<ChatState>`), `GlobalEvents` (`/ws/global`), `HistoryList` / `ChatSearch`.
- `core/state/workspace` — the web's layout (panels, tabs, dock): `WorkspaceStore` is `panel-store.ts` + `dock-actions.ts`, `WorkspaceCache` its local copy (`ppm-panels-*`) with the debounced PUT and the hydrate of `panel-utils.ts`. The blob is the one every browser of that server reads and writes, so a tab type, metadata key or field the app does not know is kept (`metadata` whole, the rest in `extra`) and written back unchanged.

The three `core` modules are plain Kotlin/JVM: their tests run on the JVM, no emulator.

## Rules the code relies on

- **One thread drives every controller.** `ChatController`, `GlobalEvents`, `HistoryList` and `ChatSearch` take a parent `CoroutineScope` whose dispatcher must be a single thread (the main one on Android, `e2e-main` in `EndToEndTest`) and must be called from it. Nothing in them is synchronized; the `StateFlow`s are what other threads may read.
- `ChatController` decodes frames on `Dispatchers.Default` and applies them back on its own thread: a `turn_events` snapshot can be megabytes.
- Two deliberate differences from the Swift code: `ChatController` keeps the reason it closed a silent socket for (Swift's `close()` reports `nil` and overwrites it), and history/frames take `now` in epoch milliseconds.
- **Tabs are the web's layout.** `AppModel` draws `WorkspaceStore`'s state; a chat tab's chat (`ChatTab`) is keyed by the layout's tab id, which is not the session id (`chat:<provider>/<session>`, or a minted id the session came to later): go through `tabSessionId` for unread, running and marking read. The one deliberate difference from `panel-store.ts`: a singleton (`settings`, `git-log`) is looked for on screen, as a table's tab is, not in other projects' keep-alive panels (see the comment in `WorkspaceStore.openTab`). A terminal tab's shell is attached when its tab is the front tab of any panel, on screen or not (`frontTabs`, the web's tab pool: a collapsed phone dock, a hidden tablet dock, a minimized window) and kept until the tab closes (`AppModel.syncTerminals`); every other kind of tab still starts only what is shown, so the server's 30-minute grace for a shell with no socket is why a terminal must not wait to be composed.
- `HttpUrl.toString()` always prints a root path (`http://host:8080/`), where Foundation prints none — tests written from the Swift ones must expect the slash.

## Drawing like the web

- Under 768 dp the phone layout (`PhoneShell`), from 768 dp the desktop one (`ui/tablet/`), as `use-is-mobile.ts`; `LocalPpmMobile` says which.
- CSS counts a border into the box; Compose's `border()` draws inside it and takes no room. A `px-2 py-0.5 border` chip is `padding(9.dp, 3.dp)` here, a `p-1` menu inside its border `padding(5.dp)`; `Modifier.edge()` (tablet) is a one-sided border that does make room.
- Inputs are 16 px only on a phone (`globals.css`). A field the tablet shows passes its class's own size as `PpmTextField(desktopStyle = …)`.
- In a `Row` measured for its intrinsic width (a menu is `IntrinsicSize.Max`), every weighted child counts as wide as the widest one: a label plus a weighted `Spacer` made a 128 px menu 168. Weight the label instead.
- What the web shows only on hover (`can-hover:` is hover **and** a fine pointer) is always shown on a touch tablet. Compare with the web under touch emulation (CDP `Emulation.setTouchEmulationEnabled`), not a desktop mouse — and expect Playwright clicks to hang while `setEmitTouchEventsForMouse` is on.
- A handle that moves with the edge it drags measures on the screen (`Modifier.screenDrag`, `TabletShell.kt`): `draggable` reports moves in the handle's own coordinates, which came to about half the finger's travel, and `drag()` drops the last stretch when the release carries it.
- Tailwind 4's bare `border` is `currentColor`, not the border token: the web's menus are outlined in the text colour, and `MenuBox` copies that. Read a colour off the page (`getComputedStyle`), not off the class name.
- `graphicsLayer(alpha < 1)` draws into an offscreen buffer the size of the element, which cuts a shadow off at its edge. An element with a shadow takes `CompositingStrategy.ModulateAlpha` (the tab drag's label).
- Every web scroller shows Chrome's overlay thumb while it overflows (`globals.css` puts `scrollbar-width: thin` on `*`, which also turns the `::-webkit-scrollbar` rules off): 4 px floored to device pixels, flush with the padding box's far edge, never shorter than it is thick, no track, never fading, taking no room. Scroll with `cssScrollY()` / `cssScrollX()`, or `cssScrollbar(listState)` on a `LazyColumn` (`ChromeScrollbar.kt`) — except where the web hides it: `scrollbar-none`, `[scrollbar-width:none]`, Radix `ScrollArea` (Settings) and Radix Select's list (`data-radix-select-viewport` is `scrollbar-width: none`). Chrome draws a scroller's own thumb over its rounded corners, past the border's curve: a rounded box puts `chromeScrollbar(state, …, border = 1.dp)` before its `clip` and scrolls after its `cssBorder`. A box scrolling both ways passes each bar the other's state (`across`): while both overflow, each stops a thumb's thickness short of their shared corner.
- `Modifier.pointerHoverIcon` takes effect when the pointer comes in: one attached while the pointer is already over it waits for the next entry. Keep it attached and change its icon (`dragCursor`).
- Toasts are sonner 2.0.7 as the web sets it up (`Toaster.kt`): its stylesheet's rule for each place in the stack, every property moved by a `CssTransition` as Chrome runs a CSS transition — from where it stands, a reversal shortened, a property the rule leaves out of `transition` set at once (a toast dropping out from behind the front changes height in one frame). Heights are exact (`cssMeasure`, 73.22 px at 2.625x), because the spread-out offsets are their sums, and a translation goes to whole pixels only while nothing scales the toast, as in Chrome; the swipe's does not, in Chrome either. Checked frame by frame against a `requestAnimationFrame` trace of the web (10-27). Two things that look wrong are the web's and kept: a leaving toast is unmounted at 200 ms while its transition runs 400–500 ms, and its corners are square (PPM defines no `--radius`). To raise the same toasts on both, a debug launch takes `--es toasts 'error:Title|Description;success~:Saved>Undo'` (`DebugLaunch.kt`: `~` times out, `>` adds an action), and on the web call, from CDP, the state dispatch on the React fiber of `section[aria-label^="Notifications"]`.
- A centred dialog (`WebDialog`) is wherever its `translate(-50%,-50%)` comes to, a fraction of a pixel whenever its height is (80vh on the tablet: 620.796875, the `max-h` kept in 64ths, puts the top on 299.203). Chrome spreads the box's own edges over two rows at that fraction, but rounds the text in it to whole pixels and snaps a body that scrolls whole. So the card's shadow, background and border are drawn in a layer of their own moved by the fraction, `CompositingStrategy.Offscreen` with room for `shadow-lg` (the resampled edge comes out at Chrome's coverage, 36/15/197 for 34/22/201), and its contents in another, from the pixel the card's top rounds to. Measured against the alternatives (10-27): one layer for both blurs every line of text; HWUI's own fractional translation keeps text sharp but blends a clipped, bordered edge twice (86 for Chrome's 34); laying the contents out from the fraction (`cssMeasure(at = top)`) rounds text as Chrome does but moves boxes a pixel, as Chrome snaps a box before translating it (1.30 against 0.99 on the member dialog). Inner boxes of a dialog that does not scroll stay crisp where Chrome spreads them. A body that scrolls must be `cssFlex()`, or the column measures it unbounded and the card runs past its `max-h`.

## Text lines like Chrome's

- Compose gives every line of a paragraph a whole number of pixels, worked out once from the first line's font (`LineHeightStyleSpan` ceils): 14 px on 20 at 2.625x is 53 px a line where Chrome's are 52.5, and a line holding a Monaspace `code` does not grow. Chrome sizes each line box from the inline boxes on it, in 64ths of a pixel, and rounds each baseline half up only as it paints it. Text that wraps where the web's does uses `ChromeText` (`ui/design`): the block's own box as a `ChromeStrut`, and `addChromeInline` / `addChromeAtomic` on the runs that size their lines differently. A `CssColumn` counts it at its exact height and tells it its phase.
- Compose's `TextAndroidCanvas` reports an endless clip, so a `StaticLayout` draws all its lines however tightly it is clipped: drawing one paragraph once per band costs lines × lines. Lines that move apart are laid out and drawn one by one (`ChromeTextLayout.lines`).
- What surrounds text — an inline code's box, a `mark`'s background, a cell's padding — snaps each of its edges from the exact baseline (`exactBaseline`), never from the pixel the glyphs went to, or it lands a pixel off half the time.
- The space above and below exact lines must be exact too: `CssColumn(top = …, bottom = …)`, not `padding` (a table cell's 4 px is 10.5 at 2.625x), and a list's outside marker must not make its item taller than its body (each 52.5 px item came out 53).
- A layout that stacks children itself — the table's rows — measures them with `cssMeasure`, which hands each its phase and answers its exact height. The table draws its collapsed borders and header backgrounds over each row's whole height, as cells measured to their content cannot.
- Compose's line-height span cannot put a baseline above the ascent Android reads from the font file, and Chrome's ascent is often a pixel less than Android's rounding of Geist's 1005 (`AscentDescentWithHacks` takes one off when the descent rounds down): 12 px text on 16 px lines sat a pixel low at 2x and 2.625x. The app's Geist files carry an ascender of 970 instead (`scripts/geist-android-ascent.py`, run after `geist-web-subsets.py`), and `PpmFonts.chromeTopRatio` works the baseline out from Chrome's metrics while rounding as Android does. Text set with no line height is centred on the font's own box, which that makes 0.035 em shorter: give it the line height the web's CSS inherits.
- `system-ui` is the system's Roboto, not Geist, and stands on Roboto's own metrics: sonner sets `font-family: ui-sans-serif, system-ui, …` on its toaster, and a window titlebar's `--x-font` falls through to `system-ui` on Android. Set such text with `FontKind.SYSTEM` (`ppmText`, `cssTightLines`), which reads the ascent and descent from the system's font file. On Geist's metrics a 13 px title sat 2 px low at 2x and right at 2.625x, so the phone alone never shows it.
- Compose measures text to the next whole pixel horizontally too: a `BasicText`'s width, `maxIntrinsicWidth` and `MultiParagraphIntrinsics` are all ceiled (`BoringLayout`'s width is an `Int`), and so are a `size(14.dp)` icon (36.75 → 37 at 2.625x) and a `padding(end = 4.dp)` (10.5 → 11). Chrome lays a flex row out with every width fractional and snaps each box only as it paints it, so a row of labels drifted right a pixel per item or two (Copy 2 px, Reply 3 px on the tablet). The exact width of a line is `getLineRight(i) - getLineLeft(i)`. Lay such rows out with `CssRow` (`ui/design`: `gap`, `start`/`end` padding, `wrap`, `centre`, and `alignEnd` for a row flush with the end of an `items-end` column, whose start Chrome rounds), its labels as `CssText`, fixed boxes in it as `Modifier.cssWidth`, and a box sized to its text at a share of the width as the user bubble's `fitWidthAtEnd`.
- What stands on the bottom of a chat is stacked from there, exactly: Chrome sizes the composer, the bars above it and the changes list before the `flex-1` transcript, so they end on the window's last pixel and each starts where the exact heights under it put it (352.52 px of composer at 2.625x). The transcript is `cssFlex(grow = true)` in a `CssColumn`, which measures the children under it first; every box in that stack has to report its exact height or the whole stack moves a pixel — `CssRow` with `top`/`bottom`/`minHeight`/`align` rather than `padding` and `Row`, `cssMinHeight` (it reads its phase: 44 px is 115 or 116 at 2.625x), `cssMaxHeight(max, lend)` for a list capped by `max-h-*` (it hands the column inside its phase), `Modifier.chromeTextArea` for the text field. In a `CssRow` a box of a set size (`cssSize`) takes the pixels between its two rounded edges, as the 36 px send button is 94 there and not 95, an icon is `cssIcon` (square at its rounded size; measured to the row's height it was squeezed to 31 of 32), and the label that truncates is `cssShrink`. Chips that are `inline-flex` in a block `div` stand on that div's strut, so the div is taller than the chip: `chipStrut` in `Composer.kt` gives the room under it (14 px at 2x, 18 at 2.625x for 16/24 Geist; none for an icon-only chip).
- A multi-line text field is `ChromeTextArea` (`ui/design`), because Compose's cannot be made to look like Chrome's: its lines are whole pixels apart (46 for Chrome's 45.5 at 2x), its padding does not scroll with the text, it brings the caret's whole line box into view inside the padding (36 px where Chrome scrolls 13: `ToEdgeIfNeeded` on the caret rect alone), and its selection path runs a line the selection continues past to the field's edge and adds the next line's margin. So the BasicTextField is laid out as tall as its text, transparent, in a box that scrolls as Chrome scrolls a textarea, and its lines, selection, placeholder and caret are drawn over it at Chrome's places; `LocalBringIntoViewSpec` stays neutral around it, or Compose scrolls the box by its own rule too. Chrome's selection on a line is the selected characters' advances — the spaces a line wraps at keep their width, which Android gives none — plus a space's width for a selected newline and for a wrap the selection runs on past (LayoutNG's `SelectSoftLineBreak`), from where the line's top rounds to and `round(line height)` tall: 46 px at 2x at all four phases measured, so a line on a half pixel overlaps the next by a row that the translucent colour paints twice. The selected text itself Chrome draws pure black (0,0,0) in light and dark alike, as the web styles no `::selection`; black drawn over the plain text would leave its antialiased edges in the text colour, so each selected line is drawn twice, clipped in and clipped out. Its glyphs start at the fractional pixel the CSS puts them on (44 px is 115.5 px at 2.625x), not at the field's whole one: drawn at the whole pixel, the phone's text sat 0.36 px right of Chrome's and differed three times as much. A focus the page gives with `focus()` scrolls the caret into view, as Chrome restores the field's cached selection and reveals it (`UpdateSelectionOnFocus(kRestore)`), while a tap's focus places the caret itself and reveals nothing more: so arming Edit on a long message shows its last line, a tap on a draft opened from its top does not jump, and the field watches the pointer, without taking it, to tell the two apart; Chrome reveals nothing for a `focus()` given while its window has no focus yet (the first page script after a cold start), so measure that with the window focused. It wraps where Blink does, not after the `/` inside a path as Android's line breaker would, through an `OutputTransformation` that lays the text out with the user bubble's invisible marks (`textareaBreakMark`), so the state, the IME, a copy and the draft hold none. Each mark replaces the character before it rather than being inserted: Compose stops a caret on both sides of inserted text, so every mark ate an arrow press (ten moved the caret nine characters), and it replaces the whole character, or a caret stepping back over an emoji would land inside it. An injected `adb shell input keycombination` with Shift brings the soft keyboard up in Chrome as in the app; `input keyevent` DPAD keys do not.
- The transcript's items are one exact stack as well: `ChatTranscriptView` puts every item (sentinel, skeleton, rows by id, live answer, idle-cache notice, trailing line) in a `CssLazyStack` keyed by item, which hands each its phase and gives it the pixels between its rounded edges. Rounded row by row, the phone's rows drifted up to 3 px from Chrome's. An item starts where the one above ends; a `LazyColumn` opened at its end measures the last item first and goes up, so there an item starts where the one below starts, less its own exact height. `SelectionContainer` is a layout of its own, so a `cssExact` inside it never reaches the `CssColumn` around it: put `Modifier.cssExact(exact)` on the container and lend the markdown inside the same `exact` (`SelectableMarkdown`).
- Known residue: Chrome's chat scroller moves its content by whole device pixels, so a message's phase is the fraction of everything loaded above it; the app's stack starts on a whole pixel at the item it measured first. A line whose exact place is within that fraction of a rounding boundary sits 1 px off the web's. Measured 10-27 on the tablet: the web's phase was .703, from rows of 532.281, 1454.516 and 1475.906 px above, and round(y) − round(y − .703) predicted every element's offset from the app, 1 px or none. Matching it needs every item above measured exactly. The same goes for where the transcript stops at its end: `use-stick-to-bottom` scrolls to `scrollHeight - 1 - clientHeight`, each rounded to a CSS px, so the web stops 0 to 2 px short of the last pixel by the fraction of the whole transcript's height; the app stops the 1 px that is on average (measured 2.45 device px at 2x against the app's 2, which put every message 1 px higher).

## Building and testing

JDK 21 (`/usr/bin/java`), Android SDK in `~/Android/Sdk`. Run Gradle outside PPM's cgroup, so that its daemon does not die with a PPM restart:

```bash
cd android
systemd-run --user --scope --quiet ./gradlew :core:protocol:test :core:client:test :core:state:test
```

The build needs bun and the repository's `node_modules` (`bun install` at the root): `ui/design`'s `buildHighlighter` makes the code highlighting's assets from them — the web's Shiki as one script for WebView's JavaScript sandbox (`SyntaxHighlighter`), and every grammar — into `build/`, so nothing generated is in git. After touching Shiki or `scripts/highlighter/`, `node scripts/check-highlighter.mjs <dir>` (header says how) checks every sample block's colours against the web's Shiki, on V8 as the sandbox runs it.

`ui/terminal-engine`'s unit tests run the real `InputConnection`, `Editable` and `KeyEvent` on the JVM under Robolectric 4.17 (`@Config(sdk = [34])`; the first run fetches Robolectric's android-all jar into `~/.m2`), and the real `ImeInputView` and `KeyboardHandler` over a mocked `TerminalEmulatorImpl`: its JNI (`libjni_cb_term.so`) is built for Android and cannot load on the host. `ImeRig`'s `FakePty` turns the emulator's dispatches into the bytes libvterm writes, and `CommittedImeInstrumentation` asserts the same literals against the real JNI on a device, so a change to either side shows up on the other.

The toolbar row's keys (`TerminalMobileToolbar`) reach the shell through `NativeTerminal.sendKey`, the emulator's own key encoder, and never as bytes written to the socket. Its queue is the one the soft keyboard commits through, so a key lands after the word `finishBeforeExternalInput` has just flushed (a direct write overtakes it), and only libvterm knows whether a program turned on application cursor keys (`ESC O A`, which htop reads and the web's fixed `ESC [ A` it does not). `EngineKeyTest` models libvterm's bytes for these keys and `CommittedImeInstrumentation` holds the model to the real JNI.

The soft keyboard is told the editor Chrome describes for xterm.js's textarea (`TerminalEditorInfo`: inputType 0x2200a1 on Android 17 and 0x200a1 before it, imeOptions 0x12000001), not `TYPE_TEXT_FLAG_NO_SUGGESTIONS`: Gboard ignores that flag on a plain text field and autocorrected "ech " to "echo " with it set, which a terminal must never do. One flag is the app's own: Chrome omits `IME_FLAG_NO_PERSONALIZED_LEARNING` (0x01000000, so imeOptions is 0x13000001), which lets Gboard learn what is typed into the web terminal, passwords at a sudo or ssh prompt included; drop it first if autocorrect ever comes back with it. Whether Gboard then composes a word or commits each key is its own call and the connection takes both, so a change here is measured on a device (`dumpsys input_method` for the numbers, the bytes the PTY reads for the typing), not by the JVM tests, which only pin the numbers.

Ctrl with a character is typed as xterm.js types it (`ControlKeys`), for a physical keyboard and the toolbar's sticky Ctrl alike, because libvterm does not: its `vterm_keyboard_unichar` (read from the shipped `libjni_cb_term.so`: the jump table sends `[ijm` to CSI u, `\]^_` to the control code, Space to CSI u only with Shift, everything else outside a-z to CSI u) folds Ctrl into a-z only, so Ctrl+[ was `ESC[91;5u`, Ctrl+I, J, M likewise, and Ctrl+C with Caps Lock on `ESC[67;5u`, all printed by a shell as text. `KeyboardHandler`'s key path and `dispatchText` are patched to call `dispatchCharacterLikeXterm`, which sends the control code as a plain character (Alt still prefixes ESC) and nothing where xterm.js sends nothing: Ctrl+Shift+letter included, so Ctrl+Shift+C interrupts nothing. `FakePty` models libvterm from that disassembly and `CommittedImeInstrumentation` holds the model to the real JNI. Enter, Tab, Backspace and Esc go through `dispatchKey`, whose literal keys libvterm writes as CSI u the moment Ctrl or Shift is held (`ESC[13;5u` for Ctrl+Enter, `ESC[127;2u` for Shift+Backspace, `ESC[1;6Z` for Ctrl+Shift+Tab; and an ESC before the Tab for Alt: `vterm_keyboard_key` and its key table in the same library), so `dispatchKeyLikeXterm` sends them as xterm.js's `Keyboard.ts` does, from the key path and from an Enter the soft keyboard commits under an armed Ctrl: Enter CR (ESC CR with Alt), Esc ESC (ESC ESC with Alt), Tab HT (`ESC [ Z` with Shift, whatever else is held), Backspace DEL (^H with Ctrl, an ESC before either with Alt), Ctrl and Shift changing nothing the web ignores. The arrows and the rest keep libvterm's `ESC[1;5D`. `SpecialKeysImeTest` runs all 32 combinations against a model of that library and `CommittedImeInstrumentation` against the real one; the legacy `ComposeMode` branches, which PPM never turns on, are left as they were.

A terminal's replay is shown and never answered. When a server picks a running shell up again, after a dropped socket or in a new process once Android killed the old one (the shell's id is kept per tab as `terminal.<server>.ppm:terminal-session:<tabId>` in the app's SharedPreferences, read ahead of the tab's own `sessionId`, and `syncTerminals` deletes it only for a tab that leaves the workspace in this process, so a cold start keeps it), it sends `{"type":"session"}` and then the shell's whole buffer as one frame, with nothing to mark its end. `TerminalController` takes the first output after a `session` frame that names the shell it asked for as the replay (a `new` shell, or an id the server replaced with another, has none) and hands it to `NativeTerminal` through `onReplay`, which calls `TerminalEmulator.writeReplay`: the parse of `writeInput`, with whatever libvterm says back dropped in `onKeyboardInput` (every answer passes that one callback, the XTWINOPS and image ones too) and an OSC 52 clipboard write not performed. Without that, a vim session's queries were answered after `am kill` (`ESC[2;2R ESC[3;1R ESC[>0;100;0c ESC[4;624;1280t ESC[6;26;16t ESC[?12;2$y`, 55 bytes typed at the prompt as text that Enter runs); the web does the same on a reconnect, with colour and focus reports on top. A shell that had printed nothing has no replay, so its first live output is taken for one and its queries go unanswered that once. `TerminalReplayTest` pins the classification and the new-process reattach, `ReplayAnswersTest` the drop over the real emulator and a modelled parse, and `CommittedImeInstrumentation` replays the queries through the real libvterm on a device (its output also lists what libvterm answers to OSC 10/11 and the focus mode, which it is not expected to answer).

A tap on nothing blurs the terminal as it does xterm.js's textarea, keyboard included, and a tap back on it types again. `leavesTextOnTap` clears the Compose focus on a tap no handler claimed. A text field's keyboard goes with its focus because Compose hides it; the terminal's editor is a plain view, and `ImeInputView.hideIme()` hides only while the view still holds the focus, so the clear is preceded by `TextInputFocus.blurNative`, which runs the `onBlur` the editor handed `takeNative` (`TerminalBody`'s: `keyboardRequested = false`, then `TerminalImeController.hideKeyboard()`) — only for the focused native editor of the tapped window. Before, the keyboard stayed up and typed nothing, and neither a tap on the terminal nor hiding and showing the keyboard helped, while the toolbar's Ctrl, which restarts the IME, did: the view ends its editor when it loses the focus (a late IME call must not reach the terminal), but `InputMethodManager` follows a view's focus only to a *different* served view (`checkFocusInternalLocked`: served view equal to next served view is nothing to do; `onViewFocusChangedInternal` does not even track a loss, read from the framework source), so the IME stayed attached to the ended editor when the focus came back. `ImeInputView.onFocusChanged` now asks the IME to start over when the focus returns to a view whose editor ended (`restartIfEditorEnded`, from `terminal_ime_patch.py`), which holds however the focus left. `View.clearFocus` hands the focus straight back to the first focusable outside touch mode (`refocus = !isInTouchMode()`), so a test window shows the refocus a finger's tap does not. `FocusImeTest` models the IME as keeping its connection until the view restarts it, `TextInputFocusTest` the contract and `NativeEditorTapTest` the order (keyboard, then focus) through the real modifier. The other half is a tap on the terminal asking for the focus back, which the web's capture-phase `touchend` does for every tap outside select mode: upstream's tap branch asked, and called `onTerminalTap`, only for a tap that cleared no selection and opened no link, so a tap that cleared a long-press selection or opened a link left an unfocused terminal unfocused and `leavesTextOnTap` blurred a focused one (nothing asked). `tap_asks_for_focus` in `patch-terminal-engine.py` moves the ask out of the `else`; `TerminalBody` ignores `onTerminalTap` while `selecting` (select mode has no `touchend`; the engine's `keyboardEnabled` is already off there). The toolbar's Paste ends in `focusTerminal()` like `handlePaste`, and does nothing at all for an empty clipboard. No JVM test: the branch is inside the engine's `pointerInput`, which needs the JNI emulator, so the check is the guarded replace (the build fails if upstream's text moves) and the tester's steps.

A blurred terminal is told it is no editor, because Android never does: one hardware letter pressed with nothing focused (blank tap, key, tap the terminal: `bisect.py` E3c/E3e) left the soft keyboard up with its cursor shown, soft taps sending 0 bytes and Gboard showing word suggestions instead of its icon row, a blank tap no longer hiding the keyboard, and only the toolbar's Tab bringing typing back; just registering a hardware keyboard did nothing (E3b), and a key pressed while the terminal held the focus never reached the IME (`onKeyPreIme` types it). Read from the framework source, not reproduced here: `InputMethodManager` keeps the IME attached to the view a tap on nothing blurred, `ImeInputStage` hands a key to the IME whenever one is bound, with or without a connection, so the key reached Gboard with the ended editor's inert connection behind it and Gboard went on composing the word; the restart the next tap triggers describes the same editor, so Gboard kept the word, and `updateSelection(0, 0, -1, -1)` was dropped by IMM as equal to the value it had cached. Soft taps then added to the stale word, which the editor refused (it rejects offsets it did not issue). Chrome ends the session instead: no connection, `TYPE_NULL`. So `ImeInputView.onFocusChanged(false)` posts `detachEditor` (`terminal_ime_patch.py`), which, if the focus is still away, restarts the IME with `onCreateInputConnection` answering `null` and `TYPE_NULL` (posted, because the focus may be going to another view that the IME starts for itself, and `restartInput` does nothing for a view it no longer serves; a focus that went and came back inside one frame finds nothing to do). When the focus returns the IME is asked for a new editor and told the caret moved to 1 and back to 0 with no composing region, which is a report IMM does not drop and Gboard does not expect, so it ends a word it still composes. `FocusImeTest` pins the order (no restart before the post, one after, a new editor and the two reports on return, an editor for a view that never had one); what Gboard does with it is the tester's: E3b/E3c/E3d/E3e/E3f, then a blank tap must hide the keyboard again and the toolbar must not be the only way back.

Select mode selects like the web's: while the toolbar's Select is on, a one-finger drag is a character selection from the cell the finger came down on (`useTerminalTouchSelection` dispatches xterm's `mousedown` at touchstart, `mousemove` per move, `mouseup` at the end, and the container is `touch-none`, so it never scrolls). `Terminal(touchSelect)` makes the engine's gesture loop start that selection when the drag passes the touch slop instead of scrolling, and takes the long press, double tap and link out of the mode; `TerminalBody` no longer calls `startSelection()` when the mode turns on (that left one cell at the cursor, `isSelecting` true, handles hidden: a drag scrolled and nothing was drawn) and no longer clears when it turns off, because the web leaves xterm's selection for Copy and the Add-to-chat popup. `TerminalTouchSelectionTest` pins what the drag selects through the real `SelectionManager`; the gesture itself is inside the engine's `pointerInput`, so the check is the guarded replace and the tester's drag.

F1 looks dead after a launch or a resume when a text field holds the focus: the sidebar's Search focuses itself on show and a new chat's box 100 ms after it appears, and the shortcuts stand aside for any focused field however it got the focus, as the web's `isTextInput` gate does (`use-global-keybindings.ts`), so Double Shift, which the web handles before that gate, is the way in. `KeyboardShortcutGateTest` pins the gate.

End-to-end tests (`EndToEndTest`) run only when a scratch server is named. `scripts/scratch-server.sh start [port]` runs this checkout's server with its own `PPM_HOME` under `/tmp` (never the real `~/.ppm`), a random password and a `demo` project, on `127.0.0.1` — which the emulator reaches as `10.0.2.2`:

```bash
scripts/scratch-server.sh start            # prints "<url> <password>"
source /tmp/ppm-android-scratch.env        # URL, PASSWORD, PROJECT
systemd-run --user --scope --quiet --setenv=PPM_E2E_URL=$URL --setenv=PPM_E2E_PASSWORD=$PASSWORD \
  --setenv=PPM_E2E_PROJECT=$PROJECT ./gradlew :core:state:test --rerun
scripts/scratch-server.sh stop
```

Sessions are created with `providerId: "mock"`, so no AI is paid for. The mock streams a code block (and an approval request) on a session's first turn and keeps its answer without them, so a first turn's text never matches its history.

The Baseline Profile in `app/src/release/generated/baselineProfiles/` is generated and committed: it lists the methods Android compiles ahead of time instead of interpreting them, and its startup half orders the dex. Regenerate it before a release when startup or the chat changed. `:baselineprofile`'s journeys (`PpmJourneys.kt`) sign in and open a mock session with a long transcript, both named in a file on the device, never in instrumentation arguments, which Gradle prints. A run replaces the directory with what its devices reached, a phone never reaches the desktop layout nor a tablet the mobile one, and one emulator runs at a time here, so generate on each and merge:

```bash
adb -s emulator-5580 push target.properties /data/local/tmp/ppm-baseline-profile.properties  # server= password= project= session=
ANDROID_SERIAL=emulator-5580 systemd-run --user --scope --quiet ./gradlew :app:generateBaselineProfile \
  -Pandroid.injected.androidTest.leaveApksInstalledAfterRun=true
cp -r app/src/release/generated/baselineProfiles /tmp/phone-profiles
# the same on emulator-5582, then
python3 -I scripts/merge-baseline-profiles.py /tmp/phone-profiles
```

Without `leaveApksInstalledAfterRun` Gradle uninstalls the app after the run, saved servers and all. `StartupBenchmarks` times a cold start with and without the profile, `ScrollBenchmarks` the frames of opening the chat and scrolling it: `./gradlew :baselineprofile:connectedBenchmarkReleaseAndroidTest -Pandroid.testInstrumentationRunnerArguments.androidx.benchmark.enabledRules=Macrobenchmark`, one test with `-Pandroid.testInstrumentationRunnerArguments.class=com.hienlh.ppm.baselineprofile.ScrollBenchmarks#scrollWithProfile`; the numbers land in `baselineprofile/build/outputs/connected_android_test_additional_output/benchmarkRelease/connected/*/*-benchmarkData.json`. On the tablet emulator the start does not depend on the code at all: it draws 2560×1600 in software, and even a fully compiled app (`cmd package compile -m speed -f`) started no faster. The phone emulator does show the profile (10-26: start 502 → 467 ms median, frame CPU P50 31.8 → 25.5 ms), and the tablet's frames do (P95 171 → 115 ms, P99 530 → 201 ms). An `adb install` compiles nothing at install (`dumpsys package dexopt` reads `verify`): ProfileInstaller writes the profile on the first start and the idle maintenance job compiles it (`speed-profile`), which `adb shell cmd package compile -r bg-dexopt com.hienlh.ppm` runs at once. `adb install-multiple` of the APK with its `.dm` (`app/build/outputs/apk/release/baselineProfiles/0/` for Android 12 and up) compiles at install, as the self-update does.

A release is the GitHub release tagged `android-vX.Y.Z` on the PPM repository, carrying the APK and its Baseline Profile as dex metadata, one `.dm` per profile format: `./gradlew :app:assembleRelease -PppmVersion=X.Y.Z`, then `python3 -I scripts/release-assets.py <dir>` names them (`ppm-android-X.Y.Z.apk`, `.api28.dm`, `.api31.dm`) and prints their SHA-256. The self-update (`AppUpdater`) takes the `.dm` for its device only with GitHub's digest and only when it holds nothing but `primary.prof`/`primary.profm` (a `.dm` may also carry verified code, which nothing but that digest would vouch for), and writes the APK as `base.apk` and the profile as `base.dm` into one PackageInstaller session, so Android compiles the update as it installs it (`[status=speed-profile] [reason=install-dm]`); without a usable profile it installs the APK alone (`verify`). Measured on the API 37 tablet: the first update goes to "Install unknown apps", which drops the installer, so the app offers "Update downloaded · Install" again when it is back in front; then "Update this app?", then Play Protect's "App scan recommended" — More details → Install without scanning, never Scan app, which uploads the APK to Google. The install ends PPM's process and leaves the launcher on screen: a session has no "Open" button at the end, as the old ACTION_VIEW install had.

## Devices

- Emulators: the AVD `PPM_Phone` on port 5580 (`emulator-5580`) and `PPM_Tablet` on 5582 (`emulator-5582`, a Pixel Tablet at 2560×1600 and 320 dpi: 1280×800 dp, the web viewport to set beside it, less the 24 dp status bar). Always pass `adb -s <serial>`.
- Never touch `emulator-5556` or any `Velox_*` AVD: they belong to other work on this machine.
- The web beside the app on the same device: Chrome on `PPM_Tablet` at `http://10.0.2.2:<port>`. Its page starts 97 dp lower than the app's window, at the same x.
- Chrome on these emulators draws a stroked SVG path with no antialiasing at all, so every lucide icon is a hard staircase there (not one partial pixel in a chevron, at 14 px or at 48), while circles, rounded borders, box-shadow rings and canvas strokes are antialiased as anywhere (a stroked SVG circle has 115 grey levels). That is the emulator's renderer, not the web's design: the app keeps its icons antialiased, as Chrome draws them on a real GPU, so compare an icon by where its strokes sit, not pixel for pixel. The edit ring's rounded corners match Chrome's to 2 px of 15 levels.
- A mouse: `adb shell input mouse` presses no button, and Compose ignores a mouse press without one. `scripts/virtual-mouse.py` registers a real USB mouse through `uinput` and plays steps on it (move, press, right press, wait, screenshot).
