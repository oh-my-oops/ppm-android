# android/ — native PPM client for Android (phone + tablet)

Plan: `plans/261019-2119-native-android-app/` (gitignored, in the main checkout). The port follows the Apple app (`~/Projects/ppm-apple/apple`, its `Packages/PPMKit` is the source of every rule here) and, behind both, the web (`src/web/`).

## Layout

- `core/protocol` — wire types. Frames are parsed into a kotlinx `JsonElement` first and read field by field (`Json.kt` extensions), so an unknown field or frame `type` never fails a decode.
- `core/client` — REST (`ApiClient` + `ApiClientSessions`/`ApiClientUploads` extensions), `SocketConnection` (OkHttp WebSocket as a channel of events, never reconnects by itself), `InflightGets` (identical GETs share one request, as `api-client.ts`), `ServerStore` (servers in a `KeyValueStore`, passwords in a `SecretStore`).
- `core/state` — `ChatTranscript` (pure reducer ported from `src/web/hooks/use-chat.ts`: frames in, `ChatEffect`s out), `ChatController` (history + socket + reconnect around it, publishes one `StateFlow<ChatState>`), `GlobalEvents` (`/ws/global`), `HistoryList` / `ChatSearch`.
- `core/state/workspace` — the web's layout (panels, tabs, dock): `WorkspaceStore` is `panel-store.ts` + `dock-actions.ts`, `WorkspaceCache` its local copy (`ppm-panels-*`) with the debounced PUT and the hydrate of `panel-utils.ts`. The blob is the one every browser of that server reads and writes, so a tab type, metadata key or field the app does not know is kept (`metadata` whole, the rest in `extra`) and written back unchanged.

The three `core` modules are plain Kotlin/JVM: their tests run on the JVM, no emulator.

## Rules the code relies on

- **One thread drives every controller.** `ChatController`, `GlobalEvents`, `HistoryList` and `ChatSearch` take a parent `CoroutineScope` whose dispatcher must be a single thread (the main one on Android, `e2e-main` in `EndToEndTest`) and must be called from it. Nothing in them is synchronized; the `StateFlow`s are what other threads may read.
- `ChatController` decodes frames on `Dispatchers.Default` and applies them back on its own thread: a `turn_events` snapshot can be megabytes.
- Two deliberate differences from the Swift code: `ChatController` keeps the reason it closed a silent socket for (Swift's `close()` reports `nil` and overwrites it), and history/frames take `now` in epoch milliseconds.
- **Tabs are the web's layout.** `AppModel` draws `WorkspaceStore`'s state; a chat tab's chat (`ChatTab`) is keyed by the layout's tab id, which is not the session id (`chat:<provider>/<session>`, or a minted id the session came to later): go through `tabSessionId` for unread, running and marking read. The one deliberate difference from `panel-store.ts`: a singleton (`settings`, `git-log`) is looked for on screen, as a table's tab is, not in other projects' keep-alive panels (see the comment in `WorkspaceStore.openTab`).
- `HttpUrl.toString()` always prints a root path (`http://host:8080/`), where Foundation prints none — tests written from the Swift ones must expect the slash.

## Drawing like the web

- Under 768 dp the phone layout (`PhoneShell`), from 768 dp the desktop one (`ui/tablet/`), as `use-is-mobile.ts`; `LocalPpmMobile` says which.
- CSS counts a border into the box; Compose's `border()` draws inside it and takes no room. A `px-2 py-0.5 border` chip is `padding(9.dp, 3.dp)` here, a `p-1` menu inside its border `padding(5.dp)`; `Modifier.edge()` (tablet) is a one-sided border that does make room.
- Inputs are 16 px only on a phone (`globals.css`). A field the tablet shows passes its class's own size as `PpmTextField(desktopStyle = …)`.
- In a `Row` measured for its intrinsic width (a menu is `IntrinsicSize.Max`), every weighted child counts as wide as the widest one: a label plus a weighted `Spacer` made a 128 px menu 168. Weight the label instead.
- What the web shows only on hover (`can-hover:` is hover **and** a fine pointer) is always shown on a touch tablet. Compare with the web under touch emulation (CDP `Emulation.setTouchEmulationEnabled`), not a desktop mouse — and expect Playwright clicks to hang while `setEmitTouchEventsForMouse` is on.
- A handle that moves with the edge it drags measures on the screen (`Modifier.screenDrag`, `TabletShell.kt`): `draggable` reports moves in the handle's own coordinates, which came to about half the finger's travel, and `drag()` drops the last stretch when the release carries it.
- Tailwind 4's bare `border` is `currentColor`, not the border token: the web's menus are outlined in the text colour, and `MenuBox` copies that. Read a colour off the page (`getComputedStyle`), not off the class name.
- `graphicsLayer(alpha < 1)` draws into an offscreen buffer the size of the element, which cuts a shadow off at its edge. An element with a shadow takes `CompositingStrategy.ModulateAlpha` (the tab drag's label).
- Every web scroller shows Chrome's overlay thumb while it overflows (`globals.css` puts `scrollbar-width: thin` on `*`, which also turns the `::-webkit-scrollbar` rules off): 4 px floored to device pixels, flush with the padding box's far edge, never shorter than it is thick, no track, never fading, taking no room. Scroll with `cssScrollY()` / `cssScrollX()`, or `cssScrollbar(listState)` on a `LazyColumn` (`ChromeScrollbar.kt`) — except where the web hides it: `scrollbar-none`, `[scrollbar-width:none]`, Radix `ScrollArea` (Settings) and Radix Select's list (`data-radix-select-viewport` is `scrollbar-width: none`). Chrome draws a scroller's own thumb over its rounded corners, past the border's curve: a rounded box puts `chromeScrollbar(state, …, border = 1.dp)` before its `clip` and scrolls after its `cssBorder`. A box scrolling both ways passes each bar the other's state (`across`): while both overflow, each stops a thumb's thickness short of their shared corner.
- `Modifier.pointerHoverIcon` takes effect when the pointer comes in: one attached while the pointer is already over it waits for the next entry. Keep it attached and change its icon (`dragCursor`).

## Text lines like Chrome's

- Compose gives every line of a paragraph a whole number of pixels, worked out once from the first line's font (`LineHeightStyleSpan` ceils): 14 px on 20 at 2.625x is 53 px a line where Chrome's are 52.5, and a line holding a Monaspace `code` does not grow. Chrome sizes each line box from the inline boxes on it, in 64ths of a pixel, and rounds each baseline half up only as it paints it. Text that wraps where the web's does uses `ChromeText` (`ui/design`): the block's own box as a `ChromeStrut`, and `addChromeInline` / `addChromeAtomic` on the runs that size their lines differently. A `CssColumn` counts it at its exact height and tells it its phase.
- Compose's `TextAndroidCanvas` reports an endless clip, so a `StaticLayout` draws all its lines however tightly it is clipped: drawing one paragraph once per band costs lines × lines. Lines that move apart are laid out and drawn one by one (`ChromeTextLayout.lines`).
- What surrounds text — an inline code's box, a `mark`'s background, a cell's padding — snaps each of its edges from the exact baseline (`exactBaseline`), never from the pixel the glyphs went to, or it lands a pixel off half the time.
- The space above and below exact lines must be exact too: `CssColumn(top = …, bottom = …)`, not `padding` (a table cell's 4 px is 10.5 at 2.625x), and a list's outside marker must not make its item taller than its body (each 52.5 px item came out 53).
- A layout that stacks children itself — the table's rows — measures them with `cssMeasure`, which hands each its phase and answers its exact height. The table draws its collapsed borders and header backgrounds over each row's whole height, as cells measured to their content cannot.
- Compose's line-height span cannot put a baseline above the ascent Android reads from the font file, and Chrome's ascent is often a pixel less than Android's rounding of Geist's 1005 (`AscentDescentWithHacks` takes one off when the descent rounds down): 12 px text on 16 px lines sat a pixel low at 2x and 2.625x. The app's Geist files carry an ascender of 970 instead (`scripts/geist-android-ascent.py`, run after `geist-web-subsets.py`), and `PpmFonts.chromeTopRatio` works the baseline out from Chrome's metrics while rounding as Android does. Text set with no line height is centred on the font's own box, which that makes 0.035 em shorter: give it the line height the web's CSS inherits.
- Compose measures text to the next whole pixel horizontally too: a `BasicText`'s width, `maxIntrinsicWidth` and `MultiParagraphIntrinsics` are all ceiled (`BoringLayout`'s width is an `Int`), and so are a `size(14.dp)` icon (36.75 → 37 at 2.625x) and a `padding(end = 4.dp)` (10.5 → 11). Chrome lays a flex row out with every width fractional and snaps each box only as it paints it, so a row of labels drifted right a pixel per item or two (Copy 2 px, Reply 3 px on the tablet). The exact width of a line is `getLineRight(i) - getLineLeft(i)`. Lay such rows out with `CssRow` (`ui/design`: `gap`, `start`/`end` padding, `wrap`, `centre`, and `alignEnd` for a row flush with the end of an `items-end` column, whose start Chrome rounds), its labels as `CssText`, fixed boxes in it as `Modifier.cssWidth`, and a box sized to its text at a share of the width as the user bubble's `fitWidthAtEnd`.
- What stands on the bottom of a chat is stacked from there, exactly: Chrome sizes the composer, the bars above it and the changes list before the `flex-1` transcript, so they end on the window's last pixel and each starts where the exact heights under it put it (352.52 px of composer at 2.625x). The transcript is `cssFlex(grow = true)` in a `CssColumn`, which measures the children under it first; every box in that stack has to report its exact height or the whole stack moves a pixel — `CssRow` with `top`/`bottom`/`minHeight`/`align` rather than `padding` and `Row`, `cssMinHeight` (it reads its phase: 44 px is 115 or 116 at 2.625x), `cssMaxHeight(max, lend)` for a list capped by `max-h-*` (it hands the column inside its phase), `cssFieldLines` for the text field. In a `CssRow` a box of a set size (`cssSize`) takes the pixels between its two rounded edges, as the 36 px send button is 94 there and not 95, an icon is `cssIcon` (square at its rounded size; measured to the row's height it was squeezed to 31 of 32), and the label that truncates is `cssShrink`. Chips that are `inline-flex` in a block `div` stand on that div's strut, so the div is taller than the chip: `chipStrut` in `Composer.kt` gives the room under it (14 px at 2x, 18 at 2.625x for 16/24 Geist; none for an icon-only chip).
- The transcript's items are one exact stack as well: `ChatTranscriptView` puts every item (sentinel, skeleton, rows by id, live answer, idle-cache notice, trailing line) in a `CssLazyStack` keyed by item, which hands each its phase and gives it the pixels between its rounded edges. Rounded row by row, the phone's rows drifted up to 3 px from Chrome's. An item starts where the one above ends; a `LazyColumn` opened at its end measures the last item first and goes up, so there an item starts where the one below starts, less its own exact height. `SelectionContainer` is a layout of its own, so a `cssExact` inside it never reaches the `CssColumn` around it: put `Modifier.cssExact(exact)` on the container and lend the markdown inside the same `exact` (`SelectableMarkdown`).
- Known residue: Chrome's chat scroller moves its content by whole device pixels, so a message's phase is the fraction of everything loaded above it; the app's stack starts on a whole pixel at the item it measured first. A line whose exact place is within that fraction of a rounding boundary sits 1 px off the web's. Measured 10-27 on the tablet: the web's phase was .703, from rows of 532.281, 1454.516 and 1475.906 px above, and round(y) − round(y − .703) predicted every element's offset from the app, 1 px or none. Matching it needs every item above measured exactly. The same goes for where the transcript stops at its end: `use-stick-to-bottom` scrolls to `scrollHeight - 1 - clientHeight`, each rounded to a CSS px, so the web stops 0 to 2 px short of the last pixel by the fraction of the whole transcript's height; the app stops the 1 px that is on average (measured 2.45 device px at 2x against the app's 2, which put every message 1 px higher).

## Building and testing

JDK 21 (`/usr/bin/java`), Android SDK in `~/Android/Sdk`. Run Gradle outside PPM's cgroup, so that its daemon does not die with a PPM restart:

```bash
cd android
systemd-run --user --scope --quiet ./gradlew :core:protocol:test :core:client:test :core:state:test
```

The build needs bun and the repository's `node_modules` (`bun install` at the root): `ui/design`'s `buildHighlighter` makes the code highlighting's assets from them — the web's Shiki as one script for WebView's JavaScript sandbox (`SyntaxHighlighter`), and every grammar — into `build/`, so nothing generated is in git. After touching Shiki or `scripts/highlighter/`, `node scripts/check-highlighter.mjs <dir>` (header says how) checks every sample block's colours against the web's Shiki, on V8 as the sandbox runs it.

End-to-end tests (`EndToEndTest`) run only when a scratch server is named. `scripts/scratch-server.sh start [port]` runs this checkout's server with its own `PPM_HOME` under `/tmp` (never the real `~/.ppm`), a random password and a `demo` project, on `127.0.0.1` — which the emulator reaches as `10.0.2.2`:

```bash
scripts/scratch-server.sh start            # prints "<url> <password>"
source /tmp/ppm-android-scratch.env        # URL, PASSWORD, PROJECT
systemd-run --user --scope --quiet --setenv=PPM_E2E_URL=$URL --setenv=PPM_E2E_PASSWORD=$PASSWORD \
  --setenv=PPM_E2E_PROJECT=$PROJECT ./gradlew :core:state:test --rerun
scripts/scratch-server.sh stop
```

Sessions are created with `providerId: "mock"`, so no AI is paid for. The mock streams a code block (and an approval request) on a session's first turn and keeps its answer without them, so a first turn's text never matches its history.

The Baseline Profile in `app/src/release/generated/baselineProfiles/` is generated and committed: it lists the methods Android compiles ahead of time instead of interpreting them, and its startup half orders the dex. Regenerate it before a release when startup or the chat changed. `:baselineprofile`'s journeys (`PpmJourneys.kt`) sign in and open a mock session with a long transcript, both named in a file on the device, never in instrumentation arguments, which Gradle prints. A run replaces the directory with what its devices reached, a phone never reaches the desktop layout nor a tablet the mobile one, and one emulator runs at a time here, so generate on each and merge:

```bash
adb -s emulator-5580 push target.properties /data/local/tmp/ppm-baseline-profile.properties  # server= password= project= session=
ANDROID_SERIAL=emulator-5580 systemd-run --user --scope --quiet ./gradlew :app:generateBaselineProfile \
  -Pandroid.injected.androidTest.leaveApksInstalledAfterRun=true
cp -r app/src/release/generated/baselineProfiles /tmp/phone-profiles
# the same on emulator-5582, then
python3 -I scripts/merge-baseline-profiles.py /tmp/phone-profiles
```

Without `leaveApksInstalledAfterRun` Gradle uninstalls the app after the run, saved servers and all. `StartupBenchmarks` times a cold start with and without the profile, `ScrollBenchmarks` the frames of opening the chat and scrolling it: `./gradlew :baselineprofile:connectedBenchmarkReleaseAndroidTest -Pandroid.testInstrumentationRunnerArguments.androidx.benchmark.enabledRules=Macrobenchmark`, one test with `-Pandroid.testInstrumentationRunnerArguments.class=com.hienlh.ppm.baselineprofile.ScrollBenchmarks#scrollWithProfile`; the numbers land in `baselineprofile/build/outputs/connected_android_test_additional_output/benchmarkRelease/connected/*/*-benchmarkData.json`. On the tablet emulator the start does not depend on the code at all: it draws 2560×1600 in software, and even a fully compiled app (`cmd package compile -m speed -f`) started no faster. The phone emulator does show the profile (10-26: start 502 → 467 ms median, frame CPU P50 31.8 → 25.5 ms), and the tablet's frames do (P95 171 → 115 ms, P99 530 → 201 ms). An `adb install` compiles nothing at install (`dumpsys package dexopt` reads `verify`): ProfileInstaller writes the profile on the first start and the idle maintenance job compiles it (`speed-profile`), which `adb shell cmd package compile -r bg-dexopt com.hienlh.ppm` runs at once. `adb install-multiple` of the APK with its `.dm` (`app/build/outputs/apk/release/baselineProfiles/0/` for Android 12 and up) compiles at install, as the self-update does.

A release is the GitHub release tagged `android-vX.Y.Z` on the PPM repository, carrying the APK and its Baseline Profile as dex metadata, one `.dm` per profile format: `./gradlew :app:assembleRelease -PppmVersion=X.Y.Z`, then `python3 -I scripts/release-assets.py <dir>` names them (`ppm-android-X.Y.Z.apk`, `.api28.dm`, `.api31.dm`) and prints their SHA-256. The self-update (`AppUpdater`) takes the `.dm` for its device only with GitHub's digest and only when it holds nothing but `primary.prof`/`primary.profm` (a `.dm` may also carry verified code, which nothing but that digest would vouch for), and writes the APK as `base.apk` and the profile as `base.dm` into one PackageInstaller session, so Android compiles the update as it installs it (`[status=speed-profile] [reason=install-dm]`); without a usable profile it installs the APK alone (`verify`). Measured on the API 37 tablet: the first update goes to "Install unknown apps", which drops the installer, so the app offers "Update downloaded · Install" again when it is back in front; then "Update this app?", then Play Protect's "App scan recommended" — More details → Install without scanning, never Scan app, which uploads the APK to Google. The install ends PPM's process and leaves the launcher on screen: a session has no "Open" button at the end, as the old ACTION_VIEW install had.

## Devices

- Emulators: the AVD `PPM_Phone` on port 5580 (`emulator-5580`) and `PPM_Tablet` on 5582 (`emulator-5582`, a Pixel Tablet at 2560×1600 and 320 dpi: 1280×800 dp, the web viewport to set beside it, less the 24 dp status bar). Always pass `adb -s <serial>`.
- Never touch `emulator-5556` or any `Velox_*` AVD: they belong to other work on this machine.
- The web beside the app on the same device: Chrome on `PPM_Tablet` at `http://10.0.2.2:<port>`. Its page starts 97 dp lower than the app's window, at the same x.
- A mouse: `adb shell input mouse` presses no button, and Compose ignores a mouse press without one. `scripts/virtual-mouse.py` registers a real USB mouse through `uinput` and plays steps on it (move, press, right press, wait, screenshot).
